# MySQL 权威配置与统一活动校验设计

## 1. 背景

当前活动与策略配置存在两类正确性风险：

1. SKU 购买入口会检查活动时间，抽奖入口只检查活动状态；仓库中另有一套未被抽奖主链调用的活动责任链，导致相同活动在不同入口上的校验结果可能不一致。
2. 活动装配和策略装配会把配置或概率区间写入 Redis，抽奖时又从 Redis 读取概率精度、默认奖池和权重奖池。MySQL 配置更新后，Redis 未重新装配或不可用都会影响抽奖结果。

本次改造只处理活动校验和配置数据源。优惠券、实物及物流发放保持现状，继续进入人工处理流程。

## 2. 目标

- 购买 SKU、抽奖、启动装配使用同一个活动有效性校验服务。
- 活动有效性统一包含：活动存在、状态启用、当前时间不早于开始时间、当前时间不晚于结束时间。
- MySQL 成为活动、策略、奖品、规则和概率配置的唯一权威数据源。
- 抽奖运行不依赖 Redis，也不要求应用启动后先完成 Redis 装配。
- MySQL 中的策略配置变更能够被后续抽奖请求直接读取。
- 保留当前概率总和、概率精度、兜底奖品、库存配置、权重规则、锁定规则和运气值规则校验。

## 3. 不在本次范围内

- 优惠券中心、实物仓储和物流供应商接口。
- MySQL 策略快照、配置版本指针和在线灰度发布。
- JVM 本地缓存或新的分布式缓存。
- 分库分表和配置中心。
- 库存桶、Outbox、RabbitMQ 和积分发放状态机改造。

## 4. 方案选择

本次采用“每次请求从 MySQL 读取配置并构建概率表”。

选择原因：

- 当前优先级是保证规则正确生效和清除 Redis 强依赖。
- 项目尚未建立配置版本号和跨实例缓存失效协议，本地缓存会重新引入配置不一致窗口。
- 概率表构建只处理单个策略的少量奖品，当前阶段可接受其计算成本。
- 后续若性能测试表明配置查询成为瓶颈，可以在 MySQL 版本化快照之上增加缓存，而不改变抽奖业务接口。

## 5. 统一活动校验

### 5.1 服务职责

新增 `ActivityEligibilityService`，它只依赖 `IActivityRepository.queryActivityById`，公开：

```java
ActivityEntity requireActive(Long activityId)
```

该方法返回已经校验通过的活动实体，并按顺序检查：

1. `activityId` 非空。
2. 活动存在。
3. `status == 1`。
4. 当前时间不早于 `beginTime`。
5. 当前时间不晚于 `endTime`。

时间边界采用包含语义：当前时间等于开始时间或结束时间时允许执行。服务通过 `Clock` 获取当前时间，生产环境使用系统时钟，测试使用固定时钟。

### 5.2 调用路径

- `ActivitySkuService.createOrder` 在读取 SKU 并创建购买聚合前调用 `requireActive`。
- `RaffleService.doRaffle` 在预占用户抽奖额度前调用 `requireActive`，并从返回实体取得 `strategyId`。
- `ActivityAmory.assembleLotteryActivity` 调用 `requireActive` 完成启动检查，不再缓存活动。

由此，购买、抽奖和启动检查共享相同的活动状态及时间语义。

### 5.3 删除废弃路径

删除没有生产调用方的活动责任链：

- `IActivityChainHandler`
- `AbstractActivityChainHandler`
- `ActivityInfoCheckHandler`
- `ActivityChainHandlerFactory`

同时从 `IActivityRepository` 和 `ActivityRepository` 删除 `cacheActivity`、`cacheGetActivity`，防止后续代码重新走旧路径。

## 6. MySQL 策略奖池

### 6.1 装配职责

`StrategyArmory.assembleLotteryStrategy` 保留启动期校验职责，但不再发布 Redis 数据。它加载同一策略的 MySQL 配置，完成全部校验后返回。

启动装配失败仍阻止错误策略静默投入使用，但运行时抽奖不依赖启动装配留下的缓存状态。

### 6.2 运行时奖池解析

`StrategyArmory` 每次抽奖构建一次不可变的策略定义，数据来自：

- `strategy`：概率精度和总概率。
- `strategy_award`：奖品 ID、概率、库存配置。
- `strategy_rule`：兜底、黑名单、权重、锁定和运气值规则。

策略定义包含：

- 默认半开概率区间表。
- 权重分组 ID 到半开概率区间表的映射。
- 奖品列表和概率精度。

三个抽奖入口使用同一加载逻辑：

- 默认奖池从默认区间表抽取。
- 权重奖池按 `groupId` 查找已校验区间表；分组不存在时拒绝抽奖。
- 排除奖池从本次加载的同一份奖品列表重新计算，避免一次请求内混用两次数据库查询结果。

### 6.3 配置并发变化

黑名单或权重规则选择与奖池读取之间仍可能发生数据库配置变更。本次不引入配置版本快照：

- 新配置完整且兼容时，本次请求使用读取到的新配置。
- 分组被删除、概率非法或奖品配置不一致时，本次抽奖失败，已预占额度由现有补偿逻辑恢复。
- 运营修改策略时仍应先完成整套配置事务，再开放流量。

## 7. Redis 清理范围

删除活动和策略对以下 Redis 数据的读写：

- 活动配置缓存。
- 策略概率精度。
- 默认概率区间表。
- 权重概率区间表。

删除 `IStrategyRepository` 中对应的存取方法以及 `StrategyRepository`、`ActivityRepository` 中的 `IRedisService` 依赖。

当前仓库没有其他生产代码使用 Redis，因此一并删除：

- `IRedisService`
- `RedissonService`
- `RedisClientConfig`
- `RedisClientConfigProperties`
- 应用和基础设施模块中的 Redisson 依赖
- `application-dev.yml` 中的 Redis 连接配置

如果未来需要限流或缓存，应以独立需求重新引入，并保证 MySQL 读取能够在缓存缺失时正常工作。

## 8. 错误与事务语义

- 活动参数非法使用 `ILLEGAL_PARAMETER`。
- 活动不存在或未启用使用现有活动不可用错误码。
- 活动未开始使用 `STRATEGY_NOT_ACTIVE`。
- 活动已结束使用 `ACTIVITY_EXPIRED`。
- 策略或奖池配置非法继续抛出配置异常，抽奖编排捕获后执行现有额度补偿。
- 活动校验发生在抽奖额度预占之前，活动无效时不会产生抽奖订单或额度扣减。

## 9. 测试设计

### 9.1 活动校验单元测试

- 空活动 ID 被拒绝。
- 活动不存在被拒绝。
- 活动未启用被拒绝。
- 当前时间早于开始时间被拒绝。
- 当前时间晚于结束时间被拒绝。
- 当前时间等于开始或结束时间时通过。
- 没有开始或结束时间的启用活动通过。

### 9.2 调用路径测试

- 购买 SKU 调用统一校验后才查询并预占 SKU。
- 抽奖调用统一校验，并使用其返回的 `strategyId`。
- 活动无效时不会调用抽奖额度预占。
- 启动活动装配只校验活动，不写缓存。

### 9.3 策略测试

- 装配有效策略时只完成校验，不调用缓存存取方法。
- 默认奖池直接使用 MySQL 返回的最新概率。
- 权重奖池从 MySQL 规则解析指定分组。
- 排除奖池使用同一次加载的策略定义。
- 两次抽奖之间修改数据库返回概率，第二次立即使用新配置。
- Redis 配置和 Redis 客户端不存在时，策略单元测试及应用编译通过。

### 9.4 回归验证

- 概率半开区间、零概率、概率精度和总和校验测试通过。
- 抽奖资格、库存桶、兜底奖、Outbox、MQ 消费和积分发放测试通过。
- Maven 全量测试通过；需要外部 MySQL 或 RabbitMQ 的条件测试可以按既有条件跳过，但必须单独报告。

## 10. 验收标准

- 购买与抽奖对同一个活动在同一时刻得出相同有效性结果。
- 已结束或尚未开始的活动不能预占抽奖额度。
- 删除 Redis 配置后，项目能够编译并运行不依赖 Redis 的单元测试。
- 修改 MySQL 策略概率或权重配置后，下一次抽奖读取新配置，无需执行 Redis 刷新。
- 代码中不再存在活动、概率精度、默认奖池或权重奖池的 Redis 读写路径。
- 当前库存、发放和退款链路行为保持不变。
