# 真实业务入口与单库闭环实施计划

## 当前缺口

1. `ActivitySkuService.createOrder` 可直接被代码调用，但没有支付系统身份校验、事件表或回调入口。
2. HTTP 抽奖接口为空，客户端身份、活动和策略绑定、幂等键均未在入口强制校验。
3. 退款后没有撤销购买资格、回收未使用次数、取消返利任务或恢复 SKU 库存。
4. 发放任务只有定时扫描；运营无法查询失败任务、重新入队或人工结案，也没有操作审计。
5. 当前机器没有可用 MySQL/Redis，配置中的远程端口也不可达，真实环境验证需要可连接的独立单库环境。

## 实现决定

- 支付回调使用 `timestamp + "\n" + rawBody` 的 HMAC-SHA256 签名。密钥只从环境配置读取，校验时间窗后才解析和处理事件。
- `payment_event` 以支付系统事件 ID 为主键，并保存请求摘要。同一事件重复通知返回首次结果；相同事件 ID 携带不同内容直接拒绝。
- 支付成功事件调用已有 SKU 授额事务。支付订单号建立全局唯一索引，避免同一支付单被绑定给多个用户。
- 抽奖 API 从已验证 JWT 的 `sub` 取得用户 ID，只接受活动 ID；领域服务从活动配置解析策略 ID。`Idempotency-Key` 必填并写入 `raffle_order.request_no`。
- 退款事务锁定原购买单，撤销待处理返利、回收有限且尚未使用的次数、恢复 SKU 库存并重算剩余购买单的日/月上限。已经使用的次数保留为风险暴露量供运营追踪。无限次数订单进入人工审核并暂停该购买资格。
- 发放任务增加用户查询、运营列表、重新入队和人工成功/失败结案。每次运营动作写入 `award_delivery_audit`。
- 真实单库验证通过显式环境变量启用，不连接到开发默认远程地址，不在未知数据库上自动执行迁移。

## 验证范围

- 单元测试：支付验签、重复事件、退款回收、JWT 身份、活动与策略绑定、发放状态机。
- 数据库测试：重复支付通知、并发抽奖、库存耗尽、发放任务重试、处理中抽奖恢复。
- 环境门槛：MySQL 与 Redis 都必须可达；迁移脚本先执行检查语句，检查结果为空后才执行 DDL。
